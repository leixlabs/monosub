## scripts/ 重构为「单一语言 + 平台内部分支」

用户要求：Windows 与 macOS 尽量用同一种脚本语言，在脚本内部区分平台；最终结构
`scripts/lib` + `scripts/release` + `scripts/publish`（build 并入 release，utils 并入 lib）。

- 全部改为 Node ESM（`.mjs`），删掉原先 macOS 的 bash 与 Windows 的 PowerShell 两套。
  选 Node 的原因：项目本身 `engines.node >= 20`，两平台都有；PowerShell 在 macOS、
  bash 在 Windows 都不自带。
- `scripts/lib/`：log / platform / paths / shell / fs / net / archive / version / xml，
  外加三个独立小工具（bump-version、check-i18n-keys、clean-temp-files）。
- `scripts/release/`：release.mjs（入口）、package.mjs（DMG / MSIX）、
  prepare-resources.mjs、verify.mjs（DMG / MSIX）、bundle-ffmpeg.mjs（macOS）。
- `scripts/publish/publish.mjs`：唯一会联网（gh）的脚本。
- package.json 命令合并为 `release` / `release:package` / `release:resources` /
  `release:verify` / `publish` / `publish:macos` / `publish:msix`（旧的
  build:dmg / build:msix / release:dmg 已移除）。

关键实现点（踩过的坑）：
- `lib/archive.mjs` 自己实现了 zip 读取/解包：Expand-Archive 在 macOS 不存在，且
  它拒收 audio.cpp/llama.cpp 那种缺目录记录的 zip。用 `pipeline + createInflateRaw`
  流式解压；但**不要**对同一个流同时 `.pipe()` 和 `for await`（实测在真实 MSIX 上
  报 "invalid block type"），`readZipEntry` 改为整段读入后 `inflateRawSync`。
- `lib/xml.mjs` 是最小化的 AppxManifest 编辑（tag 扫描 + 按偏移拼接），替代原来
  PowerShell 的 XML DOM；元素名正则必须允许 `:`（否则 `uap3:Extension` 会被当成
  名为 `uap3` 的元素）。每次 splice 后偏移失效，必须重新 `root()`/`findChild`。
- Windows 上 `spawnSync` 需 `shell: true` 才能跑 `.cmd`（tauri.cmd / npm）。
- `codesign -dv` 的输出在 stderr，校验脚本必须合并 stderr（`captureMerged`）。

## 修复：`bun run release` 报 `'C:\Program' is not recognized`

- 根因在 `lib/shell.mjs`：Windows 上无脑 `shell: true`，而 `shell: true` 会
  打开 `windowsVerbatimArguments`（Node 不再加任何引号），于是
  `C:\Program Files\nodejs\node.exe` 被 cmd.exe 拆成 `C:\Program` + 一段垃圾参数。
- 修法：**只对 `.cmd`/`.bat` 用 shell**。已经是路径或 `.exe` 的直接 spawn
  （无 cmd、无引号问题）；裸名（npm / bun / git / winapp）仍交给 cmd.exe，
  因为只有它按 PATHEXT 解析，直接 spawn 扩展名为空的 shim 会 ENOENT。
  shell 分支才用 `shellQuote()`（仅在含空白/`"`/`&|<>^` 时加引号）。
- 踩过的坑：`\"` 转义在 cmd.exe 下会**关闭引用状态**，同一参数里再有 `|` 就被
  当成管道；所以能不走 shell 就别走。
- 回归：带空格的 exe 路径、带空格+引号+`|` 的参数、裸名 npm/git、`where`
  全部通过；`verify.mjs` 对旧 MSIX 仍报那 10 项 CUDA 缺失（预期，需重打）。

## release 是否需要单独 build dist：不需要，但 dist/ 撞车是真的

## 修了 `main().catch` 的 TypeError

- `package.mjs` / `release.mjs` / `publish.mjs` 的 `main()` 是**同步**函数，
  `buildWindows()` 没有返回值 → `main()` 返回 undefined → `main().catch(...)`

  `Promise.resolve().then(main).catch(...)`。

## 本地安装报 0x800B010A：dev 证书必须进 Root 存储

- 原因：`dist/monosub_<v>_x64.msix` 是 `--no-sign` 的未签名包（给商店提交，
  商店会重签），本地 `Add-AppxPackage` 装它会因证书链无法验证而失败。
  要装的是 `--sign` 产出的 `*.signed.msix`。
- 关键：MSIX 签名是**按 Root 存储**验证的，`winapp cert install` 只写
  TrustedPeople，**不够**，必须把 `.cer` 导入 `Cert:\LocalMachine\Root`。
- **修了一个会反复触发这个错的坑**：dev 证书原先生成在 `stagingDir`
  （`build/msix`，每次构建都 `remove` 清空），所以每次跑都换一张新证书，
  之前导入 Root 的那张随即作废 → 下次安装必然 0x800B010A。
  已把证书挪到 `build/devcert.pfx|cer`（`lib/paths.mjs` 新增
  `devCertPfx`/`devCertCer`），配合 `--if-exists skip` 跨构建复用，只需导入一次。
  `winapp cert generate` 会自己写 `build/.gitignore` 忽略 `devcert.pfx`。
- 安装三步（管理员 PowerShell）：卸载旧包 → `Import-Certificate ... -CertStoreLocation
  Cert:\LocalMachine\Root` → `Add-AppxPackage <signed.msix>`。

## 「插件化/用户自下载」能否规避模型许可限制（重要结论）

用户提问：模型都是插件形式、用户自己下载的，是不是就能避开 license 限制？
答案：**部分可以，但两个坑绕不过去。**

**有效的部分**：版权许可约束的核心行为之一是 reproduce & distribute。不捆绑权重、
由用户自行获取 → 未行使分发权 → 不构成直接侵权。也不触发 Tencent HY / Llama
Community / LFM 里"禁止转售模型能力/托管 API 服务"条款。**这个收益是实在的，
当前架构已经拿到了。**

**绕不过去的部分**：
1. **诱导/帮助侵权（Grokster 标准，MGM v. Grokster, 545 U.S. 913 (2005)）**：
   自己不分发也可能担责，若"积极诱导"第三方侵权。法院看三点：① 分发工具是否以
   促成侵权为目的；② 是否采取积极措施促进侵权；③ 是否从中获经济收益。
   MonoSub 现状踩到 ②③ —— `crisperwhisper_2_large_*` 是 `tier: recommended`
   （产品主动推荐 NC 模型）+ UI 一键下载（积极促进）+ 应用付费售卖（经济收益）。
   **所以"用户自己下载"不自动豁免，推荐什么、怎么引导才是关键变量。**
2. **地域排除不受下载方式影响**：Tencent HY 的 EU/UK/KR 排除是**授权范围（territory
   of grant）**限制，不是分发方式限制。谁下载都一样，法国用户就是没有授权。
   插件化在这条上给**零保护**，只能靠地域路由或换默认模型。
3. **AUP / 使用限制跟着材料走**（Gemma、NGC、Llama AUP、Youdao 阈值）—— 与获取方式无关。
4. **无许可证的 8 个模型反而更糟**：无 grant，主动列入 + 提供一键下载比被动提及更像
   组织获取。
5. **署名义务由 UI 触发**，与谁下载无关（见上一条更正）。

**推荐姿态**：不是"靠插件化规避"，而是「**不分发 + 不诱导 + 显式告知**」三件套：
不捆绑（已做到）、NC 模型不进 default/recommended、行内打风险徽标、下载前确认弹窗
展示许可证与限制、附用户自担声明。这套组合打的是 Grokster 的"积极诱导"要件 ——
证明你没有促进侵权，反而在提示风险。

**额外实操闸门**：Apple / Microsoft 商店审核不看版权法论证。付费应用在运行时拉取
第三方非商用权重，本身就是审核风险。

## GPLv3 FFmpeg 争议：用户拿 Gemini 结论质疑，已澄清并更正本审查的过度断言

用户引用 Gemini 结论「GPLv3 不禁止商业售卖，§4 允许任意定价，开源+商店售卖完全合规」
来质疑 P0 判定。**结论：Gemini 那句话本身正确，但答的是另一个场景。**

- **场景 A（Gemini 答的）**：自己的软件**整体**以 GPLv3 开源 → 商店收费卖 → ✅ 完全合规。
- **场景 B（MonoSub 现状）**：App 闭源（且无 LICENSE）**捆绑** GPLv3 二进制 →
  问题不是"能不能收费"，而是"闭源应用能否 convey GPLv3 二进制"，归 §5/§6/§10 管。

**更正本审查的过度断言**：FFmpeg 是**独立子进程**调用，非链接入库——
`transcribe.rs:1713` `tokio::process::Command::new(ffmpeg)`、
`video.rs:383` `Command::new(&ffmpeg_cmd)`。
按 §5 末段 **aggregate** 条款 + FSF "arm's length" 立场，大概率构成聚合而非衍生作品，
**§5(c) 传染条款不必然触发**。先前写的"直接违反 §5(c)"说过头了。

**但仍是 P0，因为聚合豁免有条件，两个条件都不满足**：
1. §4/§6 义务不因聚合免除：附版权声明 + GPLv3 全文 + Corresponding Source（含构建脚本）
   或 ≥3 年书面要约。现状一条未履行。
2. §5 聚合豁免条件要求不得限制用户权利超出各作品自身许可；**§10 禁止 further
   restrictions**。Mac App Store LA EULA 限"Apple 品牌设备 + 个人非商业用途 + 家庭共享
   数量"→ 与 §10 冲突。FSF 立场：两者不可兼得（2011 VLC 撤下 App Store 即此问题）。
   → **恰恰因为要上 Mac App Store，GPLv3 绝对不能留。**

**新发现（范围扩大）**：**macOS 侧同样是 GPLv3，不只 Windows**。
`bundle-ffmpeg.mjs:33` 用 `brew install ffmpeg`，Homebrew 官方 formula `license` 字段就是
`GPL-3.0-or-later`；homebrew-core 切 LGPL-only 的 PR #276228 CI 挂了未合入。
→ 两个平台都要换，不能只修 Windows。

**澄清一个混淆**：整体 GPLv3 化**解决不了模型许可**。模型权重是独立作品，
CC-BY-NC / Tencent HY / Llama Community / LFM 不受 GPLv3 影响。
且整体开源会反噬商业模式——任何人可合法免费再分发未签名版，而商店版卖的正是
"已签名公证/免 Gatekeeper/自动更新"。

**正解**：换 **LGPL** 构建，且**零功能损失**——实测实际调用参数只有
`["-acodec","pcm_s16le","-ar","16000","-ac","1","-y"]`（原生 PCM），
缩略图与 ffprobe 元数据也是原生能力；编进去的 x264/x265/xvid/vidstab 从未调用。
换完后仍需：附 LGPL-2.1 全文 + 版权声明 + 源码（或书面要约）+ 保留替换可能
（当前"独立可执行文件 + `MONOSUB_FFMPEG_PATH` 覆盖"架构天然满足）。

## 事故：扁平遗留的 CPU-only 引擎盖住了 CUDA 构建

**症状**：dev 跑转写，VAD 阶段正常，ASR 报
`audiocpp_cli failed: CUDA backend requested but it is not registered in this build
(available: CPU:0 ...)`。

**根因**：`resources/bin/` 里还留着一份**旧布局的扁平**
`audiocpp_cli-x86_64-pc-windows-msvc.exe`（25 MB，`--version` 显示 `backends: cpu`，
Oct 7），而 `find_executable` 的候选展开是
`flat_map(|c| [dir.join(c), nested.join(c)])` —— **扁平优先**。于是：
扁平 CPU 构建胜出 → 引擎没注册 CUDA → 等到用户排进文件才报错。
`target/debug/resources/bin` 也有同一份（tauri dev 用的那份）。

**为什么之前没暴露**：三层目录改造（`bin/<engine>/`）只保证新脚本装到子目录，
没人清理旧脚本留下的扁平文件；两个位置都有，谁先被解析就用谁。

**修复（三处，都做了回归护栏）**
1. `engine/cli.rs::find_executable`：改为 **`<dir>/<binary>/<candidate>` 优先**，
   扁平兜底（ffmpeg/ffprobe/yt-dlp/monosub-cli 和 macOS 仍走扁平）。
   新增测试 `the_engine_directory_beats_a_flat_leftover`（临时目录里同时放两份，
   断言解析到子目录那份），测试注释写明了这次事故。
2. 删除两处 bin 的遗留文件：扁平的 `audiocpp_cli-*.exe`、`llama-server-*.exe`，
   以及文件名在引擎子目录里也存在的扁平 DLL（llama*/ggml*/mtmd/libomp）。
   **msvcp140*/vcruntime*/vcomp* 故意保留**——那是 ffmpeg 等要用的扁平 MSVC 运行时。
3. `prepare-resources.mjs` 新增 `pruneStaleFlatEngines()`（每次 Windows 构建先跑，
   幂等）；`verify.mjs` 若包内出现 `resources/bin/(audiocpp_cli|llama-server)-*.exe`
   直接判失败。另外 `committed_cli_path()` / llama 的 dev 解析测试改为
   **Windows 断言子目录路径、macOS 仍断言扁平**。

**注意**：`engine::vad::tests::real_cli_*` 的 2 个失败是既有环境问题
（spawn 捆绑二进制 `PermissionDenied os error 5`），与本次无关，改动前就在。

## CUDA 版本最终定案：只发 13.3 / 13.4（12.4 试过又回退）

**最终决定（用户 2026-10-26 16:35）**：只发 CUDA 13.3（audio.cpp）+ 13.4（llama.cpp），
**Pascal（GTX 10 系）及更老明确不支持**。理由被用户认可：那批卡 8 年+、跑 ASR 本来就慢；
而 12.4 让 50 系失去原生 kernel 且 fatbin 大 1.3 GB。曾短暂切到 12.4（见下），已完整回退：
`prepare-resources.mjs` 的 pin/探测前缀、`verify.mjs` 的 DLL 断言、`gpu.rs` 的阈值
（6.1→7.5）、`scripts/README.md`、以及 `resources/bin` 与 `target/debug/resources/bin`
的引擎实物（从 `%TEMP%\monosub-cuda124\backup-*` 还原）。`commands/cuda_pack.rs` 与
`cuda-pack.json` 生成逻辑（当时在做的"按需下载加速包"）已删除。

**关键技术事实（下次别再绕）**：CUDA 13 ≠ 只支持 50 系。它是 **Turing(7.5) → Blackwell(12.0)**。
"13.x 向下兼容"指的是运行时/驱动，不是编译目标：CUDA 13.0 Release Notes §2.5.2
removed offline compilation and library support for Maxwell/Pascal/Volta，所以 13.x
的 fatbin 里根本不可能有 sm_61，GTX 1080 会报 `no kernel image is available`。
另：CUDA 13 随 **R580 分支**驱动发布，那是最后一个支持 7.5 之前 GPU 的分支。

**UI 配套**：`CudaNotice` 现在区分"装驱动能修"和"卡太老"——`compute_capability_too_low`
时不再显示"安装驱动"按钮（换驱动没用），改为 `fileList.cuda.tooOldHint`（提示需要
Turing 或更新），避免把 GTX 10 用户送去 NVIDIA 下载页白折腾。

## （已回退）CUDA 13.3/13.4 → 12.4（一度按"覆盖面优先"实施）

**依据（两家的 CMAKE_CUDA_ARCHITECTURES 是显式 pin 的，不是猜的）**
- audio.cpp v0.9.1 workflow：`12.4 → 61-virtual;70;75;80;86;89;90`，`13.3 → 75;80;86;89;90;120`
- llama.cpp b11696 交给 ggml 默认：12.4 时 = `50/61/70/75/80/90` 虚 PTX + `86/89` real，**无 120**

→ 12.4 换来 Pascal（GTX 10 系）+ 更低驱动门槛，代价是 **sm_120（RTX 50 系）没有原生 SASS**，
只能靠 `90` 那条的 compute_90 PTX 由驱动 JIT。

**实测（本机 RTX 5080，cap 12.0）**：12.4 的 audio.cpp 真跑通了。
- 首次：wall 16.8s（含 JIT + 建缓存），之后 **173ms**；同输入 13.3 是 358ms → 没有性能回退
- `llama-server --list-devices` 正常枚举 CUDA0；`audiocpp_cli --version` backends: cpu,cuda
- JIT 结果会落在 `%APPDATA%\NVIDIA\ComputeCache`，所以只有第一次慢

**改动**
- `prepare-resources.mjs`：两组 pin（audio bin/cudart、llama bin/cudart）换成 12.4 + 新 sha256
  （都对着 GitHub API 的 digest 校验过）；`engineInstalled` 探测前缀改成
  `cublas64_12/cudart64_12/cufft64_11`（**故意带版本**：残留的 13 目录不能被当成"已安装"）；
  文件头新增「为什么 12.4 不是 13」一节，含 12.8 的建议回归条件。
- `verify.mjs`：`cudart64_12/cublas64_12` 精确断言；cufft 改成按族匹配
  （cuFFT 自己的 major 是 11，不跟 toolkit 走）。
- `commands/gpu.rs`：`MIN_COMPUTE_CAPABILITY` 7.5 → **6.1**（audio.cpp 的 fatbin 起点），
  并补两条测试：Pascal 接受、Blackwell（12.0）走 PTX 接受。
- `scripts/README.md`：架构对照表 + 取舍说明。
- 本地 `resources/bin/{audiocpp_cli,llama-server}` 与 `target/debug/resources/bin` 的对应目录
  已换成 12.4 实物（dev 用的是 target/debug 那份）；旧的 13.x 目录备份在
  `%TEMP%\monosub-cuda124\backup-*`，可回滚。

**包体代价（实测压缩率）**：`ggml-cuda.dll` deflate 后 audio 245→433 MB、llama 135→253 MB，
即安装包约 +300 MB；解压后磁盘占用 1.7 GB → 3.1 GB。PTX 文本压缩率高，所以原始体积涨得多
（+1.3 GB）但下载涨得少。

**不能"用系统里更新的 CUDA"**：exe 的导入表写死 `cudart64_12.dll`，CUDA 13 的库叫
`cudart64_13.dll`，名字/ABI 都不通；且 Windows 先查 exe 目录，随包那份永远优先。
随机器变化的只有**驱动**（系统唯一，本来就用它的）。想真正用上 120 原生内核只能同时打包
两个 `ggml-cuda.dll`，但 MSIX 安装目录只读、无法运行时替换，且 +400 MB。

## 空状态新增 CUDA 可用性检测（Windows）

用户在文件列表空状态「拖到窗口即可添加」下方要求显示 CUDA 检测结果，失败时引导安装。

- 新 Rust 模块 `commands/gpu.rs` + 命令 `cuda_status`（已注册进 main.rs 与 AGENTS.md）。
  探针是 `nvidia-smi --query-gpu=name,driver_version,compute_cap --format=csv,noheader`：
  **它随驱动安装**，所以「找不到」就是「没装驱动」这个答案本身；5 秒超时。
  `applicable` 在非 Windows 为 false（macOS Metal / Linux CPU 用不到 CUDA），前端据此不渲染。

  Maxwell/Pascal/Volta（sm_50–sm_70）。**算力解析不出来（N/A）不判失败** ——
  能跑 nvidia-smi 说明驱动在，误报「太旧」会白让用户重装驱动。
  stderr 含 "no devices" → `no_gpu`，其余非零退出 → `probe_failed`（带截断 detail）。
- `reason` 是稳定机器码（ok / not_windows / no_driver / no_gpu /
  compute_capability_too_low / probe_failed），句子交给前端 i18n 拼 —— 否则中文界面
  会冒出英文断言。
- **只提示，不阻断**：真正的判据是引擎自己的退出码。
- 前端 `src/lib/gpu.ts`（结构 + 会话内缓存，`refresh` 为重新检测路径，失败清缓存）+
  `src/components/CudaNotice.tsx`（就绪一行小字 / 失败一张警示卡：原因 + 「CUDA 运行库
  已随 App 附带，只需装驱动」+ 驱动下载页 + 重新检测）。挂在 `FileList` 空状态
  `fileList.addVideos` 下方。

- 本机实测 RTX 5080 / 617.42 / 12.0 → 显示「CUDA 加速已就绪 · NVIDIA GeForce RTX 5080」。

## CLI 落地名去掉三元组后缀：`monosub-cli-x86_64-pc-windows-msvc.exe` → `monosub-cli.exe`

用户反馈「最终的执行文件能不能简化，直接是 monosub-cli，这样在 PATH 中更好执行」——
这不只是 UI 文案问题，是个真 bug：Windows 便携/自编译时 `cliInstallCommand()`
把 `resources/bin` 加进用户 PATH，但那里的文件叫 `monosub-cli-<triple>.exe`，
敲 `monosub-cli` 根本解析不到。MSIX 走 App Execution Alias 所以掩住了这个坑。

- Rust `engine::cli::monosub_cli_file_name()` 改为裸名（Windows 加 `.exe`）。
  `target_triple()` 仍被 `binary_candidates()` 使用，没删。
- 打包脚本：`scripts/lib/platform.mjs` 新增 `cliName`（不带三元组）；
  `package.mjs` 两处 `bundledName('monosub-cli')` → `cliName`（含 MSIX 别名
  Executable 路径）；`verify.mjs` 的 `requireEntry` 与 macOS 的
  `startsWith('monosub-cli-')` 查找同步改为精确 `cliName`。
- 引擎（audiocpp_cli / llama-server / yt-dlp / ffmpeg）**保持** `-<triple>`：
  只有 `resolve_bundled_binary` 解析它们，而 `binary_candidates()` 会同时试
  裸名与带后缀两种，所以不需要动。
- UI：CLI 卡片里原来那行超长绝对路径（dev 下是 `…/src-tauri/resources/bin/…`）
  换成裸命令 chip `monosub-cli`（`fileName` 去 `.exe` 派生），完整路径降为
  `title` 悬浮。测试 id `settings-cli-path` → `settings-cli-command`。
- 本地 dev 产物已手动改名（`src-tauri/resources/bin` 与
  `target/debug/resources/bin` 各一份，均 gitignore），否则卡片会显示「未随包」。
- 文档：`paths.rs` 两处注释、`AGENTS.md` §resources、`docs/tech-spec/cli-design.md`
  与 `microsoft-store-publish-spec.md` 各加「已变更」注记（不改写历史正文）。

## 排查：`model plan selected` 为什么没有 `[disabled]`

结论：不是 bug。应用日志（`%APPDATA%/MonoSub/logs/monosub.2026-10-26.log`）里
上面一行就是 `Starting transcription task ... enable_diarization=true`，即请求确实开着
说话人分离，所以 `diar=nemotron_3_diar_q8_0` 不带后缀是正确的。

链路：`file.diarization` 入队时由 `settings.defaultDiarization` 播种
（`lib/fileImport.ts:68`），store 默认值 `true`（`store/useStore.ts:378`）；Settings ▸ 模型
的开关改的就是这个默认值（`SettingsModelPlan.tsx:272`），冻结进 `settings.json` 的计划也是
`diarization: true` + diar/turns 步骤。`[disabled]` 只在 `transcribe.rs:477` 的
`!enable_diarization && plan 含 Diarize 步骤` 分支里加；plan 无 diar 模型则是 `none`；
CLI 永不带 `[disabled]`。

后续：用户坚持创建任务时行内开关是关闭的。再查日志：08:46:06 与 08:46:35 两次
`enable_diarization=true`，中间 29 秒该行处于 `error`（qwen3 未安装）——而
`FileItem` 的开关只在 `status === 'pending'` 渲染，所以那段时间行内根本没有开关可拨，
第二次是由缺模型弹窗的「开始转录」直接复用了入库时的值。修复：`FileItem.tsx` 把
开关的渲染条件放宽到 `pending || error`（`processing`/已完成仍不显示），让"失败后重试"
这个真正做决定的位置可以改值。`bun run check` 通过。
